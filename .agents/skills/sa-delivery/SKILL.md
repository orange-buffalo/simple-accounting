# SA delivery

The repository controller owns the review/fix loop. Do not substitute an informal self-review or invoke CE's publishing workflows.

1. Read `AGENTS.md` and `docs/AgentHarness.md`. Clarify requirements that cannot safely be inferred. Record acceptance criteria and the current `git rev-parse HEAD` **before editing**. Preserve the original criteria, including subsequent user clarifications, in the review request. For a review of existing branch commits, use their explicitly selected base instead of HEAD.
2. Before coding, read the complete active catalog in `.harness/prevention.json` (also injected by the plugin) and identify relevant constraints in the implementation approach. Apply its scoped rules and exceptions during implementation, not only review. Implement using repository conventions and appropriate tests. Preserve unrelated changes. Never invoke Bun directly. Regenerate GraphQL artifacts with the Gradle tasks in `AGENTS.md`. The primary implementation agent runs the appropriate Gradle validation and checks its results, including after controller repairs, and inspects applicable rendering reports. Do not delegate test-pass verification to reviewers.
3. Before EVERY review round, the primary implementation agent (orchestrator) must finish self-review, wait for ALL relevant tests to complete, check their results, and finish all own verifications (including applicable rendering inspection). Resolve failures before launching reviewers; never overlap pending validation with delegated review. Then call `sa_review` with original requirements, recorded base SHA, review profile, and `preflight: { selfReviewCompleted: true, testsCompleted: true, verificationsCompleted: true }`. These are completion attestations, not test logs or receipts; do not set them while work remains. Prefer `targeted` with explicit fully qualified `testClasses` for bounded application changes; `full` for unbounded scope; `harness` only for harness/docs. The controller launches two independently operating full reviewers with identical configuration covering functional, security, code and UX aspects, plus two prevention.json compliance reviewers in the same parallel batch. It validates/deduplicates findings and applies bounded repairs. Reviewers inspect source-level coverage only, never build/test results or pass/fail evidence.
4. After `sa_review` returns `awaiting-verification`, repeat orchestrator self-review, rerun the selected Gradle validation after repairs (`fixes > 0`), wait for all relevant tests, check results and finish every own verification before resuming with the SAME run ID and fresh preflight attestations. Inspect regenerated rendering reports when applicable. The controller never starts the second round automatically after repairs. If validation exposes a defect, repair it before resuming when rounds remain. A review receipt alone is not sufficient. If rounds are exhausted, finish implementation and validation and disclose the review limitation; do not stop solely because the review budget is exhausted.
5. Hand over the returned status, run ID, evidence paths, and unresolved findings. Review at most two rounds per implementation or distinct human-feedback turn (initial review plus one re-review). New user review feedback supplied as a clarification starts a fresh turn on the same run, resetting round, repair, time and cost limits while retaining cumulative usage, evidence, original requirements and base. Duplicate feedback and ordinary continuation do not reset limits. Each new turn refreshes approved lessons and reviews cumulative session changes, checking earlier-turn code for analogous issues under those lessons. Never invent feedback or restart under a new ID to evade limits. Exhausting a turn stops only automatic review: finish required fixes and validation and report the limitation without claiming a clean receipt. Ask for direction only for genuine ambiguity or external blockers. Edits after a passed receipt need review; new human feedback renews the turn even after a passed or exhausted receipt.
6. Commit each implementation turn's completed changes as a separate commit under `AGENTS.md`, including review corrections. Explicit user instructions override this default: "do not commit" suspends automatic commits until authorized. Include only relevant agent changes and keep separate turns separate. Do not push, publish, or merge unless requested. Scoped authorization covers only its stated scope. Use the existing PR/release skills only on explicit request.

## Human review feedback

For corrections to an earlier reviewed implementation, first retain its run ID. Apply accepted corrections and call `sa_learn` with the original run ID and human feedback before reviewing, so verified prevention is available to that turn's reviewers. Resume `sa_review` with the same original contract and distinct user feedback as clarification; review cumulative corrected changes, including analogous issues in earlier-turn code. Then commit the completed turn under `AGENTS.md`. Diagnose whether knowledge was missing, ignored, ambiguous/new, or an execution/tooling failure. Reuse existing guidance or choose a concrete workflow/automation remedy before adding rules. Learning independently verifies scoped curation; it does not prove measured improvement. Do not add an unverified candidate to `AGENTS.md` or the active catalog.

If a comment adds a new requirement rather than identifying a miss, record it as specification evolution. If no original run exists, acknowledge the missing evidence; never invent a reviewer failure explanation.

Every human comment must be investigated, corrected or clarified with the user, and included in learning. Never dismiss feedback on your own. If you disagree, ask with arguments, reasoning and options. Learn explicit user preferences as independently verified policy, without falsely claiming measured reviewer improvement. Follow `sa-feedback` for indexed batch input and unresolved learning questions. After corrections, always provide the feedback report table with ref index, file:line, initial user comment and concise agent action including lesson status. Carry unresolved prior comments forward.

All delegated implementation/review agents must receive the current approved knowledge bundle. On other harnesses without the executable controller, report automation unavailable rather than pretending these steps were enforced.
