# SA delivery

The repository controller owns the review/fix loop. Do not substitute an informal self-review or invoke CE's publishing workflows.

1. Read `AGENTS.md` and `docs/AgentHarness.md`. Clarify requirements that cannot safely be inferred. Record acceptance criteria and the current `git rev-parse HEAD` **before editing**. Preserve the original criteria, including subsequent user clarifications, in the review request. For a review of existing branch commits, use their explicitly selected base instead of HEAD.
2. Implement using this repository's conventions and appropriate tests. Preserve unrelated changes. Never invoke Bun directly. Regenerate GraphQL artifacts with the Gradle tasks in `AGENTS.md`. The primary implementation agent runs the appropriate Gradle validation and checks its results, including after controller repairs, and inspects applicable rendering reports. Do not delegate test-pass verification to reviewers.
3. Call `sa_review` with the original requirements, recorded base SHA, and review profile. Prefer `targeted` with explicit fully qualified `testClasses` when affected backend/API/full-stack scenarios can be identified. Use `full` only for an unbounded blast radius. `harness` is only for changes wholly contained in the agent harness/docs. Profiles/testClasses describe scope; they never schedule builds or tests. The controller runs configured-model functional, security, code and UX reviewers in parallel, then independently validates submitted findings, applies bounded fixes and re-reviews. Reviewers inspect source-level coverage only, never build/test results or pass/fail evidence. A passed review receipt is not a build/test validation receipt.
4. After `sa_review` returns, if it applied repairs (`fixes > 0`), the primary implementation agent must rerun the selected Gradle validation and check its results before handover; inspect regenerated rendering reports when applicable. A review receipt alone is not sufficient. If validation exposes a defect, repair it and resume with the existing run ID when rounds remain. If rounds are exhausted, finish implementation and validation and disclose the review limitation; do not stop solely because the review budget is exhausted.
5. Hand over the returned status, run ID, evidence paths, and unresolved findings. Review at most two rounds (initial review plus one re-review); do not bypass this by silently restarting. Exhausting review rounds stops only automatic review, not implementation: finish required fixes and validation and transparently report that the review limit was reached without claiming a clean receipt. Ask for user direction only for genuine ambiguity or external blockers. New human feedback supplied as a clarification renews expired time or exhausted cost budgets, retaining previous usage and evidence; repeated feedback and ordinary continuation do not. This does not reset rounds or repairs. Do not otherwise silently extend the budget or restart under a new run ID. Resume only with the existing run ID. After a passed receipt, subsequent edits need review if rounds remain; if exhausted, complete validation and report the receipt no longer covers the final source.
6. Commit each implementation turn's completed changes as a separate commit under `AGENTS.md`, including review corrections. Explicit user instructions override this default: "do not commit" suspends automatic commits until authorized. Include only relevant agent changes and keep separate turns separate. Do not push, publish, or merge unless requested. Scoped authorization covers only its stated scope. Use the existing PR/release skills only on explicit request.

## Human review feedback

For corrections to an earlier reviewed implementation, first retain its run ID. Apply accepted corrections and review the corrected state. Call `sa_learn` with the original run ID and the human feedback, then commit the completed turn under `AGENTS.md`. It investigates raw reviewer and synthesis artifacts, independently checks the findings, evaluates proposed guidance against blind replay/variation/clean cases, and records a verified lesson or an unpromoted candidate. Do not add an unverified candidate to `AGENTS.md` or the approved knowledge registry.

If a comment adds a new requirement rather than identifying a miss, record it as specification evolution. If no original run exists, acknowledge the missing evidence; never invent a reviewer failure explanation.

Every human comment must be investigated, corrected or clarified with the user, and included in learning. Never dismiss feedback on your own. If you disagree, ask with arguments, reasoning and options. Learn explicit user preferences as independently verified policy, without falsely claiming measured reviewer improvement. Follow `sa-feedback` for indexed batch input and unresolved learning questions. After corrections, always provide the feedback report table with ref index, file:line, initial user comment and concise agent action including lesson status. Carry unresolved prior comments forward.

All delegated implementation/review agents must receive the current approved knowledge bundle. On other harnesses without the executable controller, report automation unavailable rather than pretending these steps were enforced.
